Who does what, and what it costs

The research purpose is to create a pipeline with increased accuracy ont eh FINDVER benchmark, but also determining which work belongs which of the three options (edge, cloud, or script)

Edge

Qwen2.5-Coder-3B on the laptop via Ollama. Handles structured, templated work: splitting claims, writing table lookups, filling output templates.

$0 · unlimited · 19 tok/s in, 6.7 out

Cloud

DeepSeek / Qwen APIs. Reserved for judgment: deciding what evidence a claim needs, synthesising across sources, writing the final explanation.

paid per token · escalation only

No model

Plain Python. Similarity ranking, BM25, table parsing, code execution, arithmetic re-checks, all control flow. Free and instant.

03

Four notes after testing

All four came from actually running the code rather than reading the paper. Each one changed a previous assumption.

  • Good news · saves days of work

    The tables are stored as HTML

    The paper says tables get flattened into lines of text, so I'd planned to write a parser to rebuild them into a usable shape. The actual files turn out to keep every table as HTML, about 83 per document, and Python reads that straight back into a spreadsheet in one line.

    So that job mostly disappears, and the time moves to the search problem instead, which is harder and more interesting.

  • Trap · caught before it did damage

    The examples aren't shuffled

    Every false claim is listed first, then every true one. So taking the first hundred examples to test on gives you a hundred false ones, so a model that blindly answers "false" every single time scores a perfect hundred percent.

    So every sample is now drawn evenly across both answers, with a check that runs before the experiment does.

  • Useful · free evidence

    The dataset shows its working

    For every claim involving numbers, the people who built the dataset included the actual calculation they ran and the answer it gave. They didn't verify these claims by reading and reasoning about them; they verified them by doing the arithmetic in code.

    So there's a good argument that we should too. It also lets me score whether the maths was right separately from whether the final answer was right.

  • Surprise · changes a decision

    The small model did better than I assumed

    Given the whole job with no help from a cloud model, it found the right table, added four figures together correctly, spotted the contradiction and gave the right answer. But part of its written explanation argued for a point its own conclusion didn't actually rest on.

    So: right answer, shaky reasoning, exactly what the explanation-checking step exists to catch. And the line between the local and cloud model is something to test rather than guess at.

0b The starting number The simplest possible version runs twice, once entirely on the laptop and once entirely in the cloud. 1 Tables and arithmetic This stage turns every table into something the model can look up by row and column name, and moves all the arithmetic out of the model and into Python. The two belong together, because a number fetched from the wrong cell guarantees wrong arithmetic afterwards no matter how good the calculator is. table_parser.pytable_cache/sandbox.pyskill_lookup.py Wrong numbers pulled from tables, and wrong sums done on them.
2 Finding the right evidence The search step decides which parts of a very long filing the model ever gets to see, so a claim whose evidence it misses is unanswerable regardless of how good the reasoning is. The published approach finds everything it needs only about 68 percent of the time, and so far nobody has tried to improve on that. retriever_bm25.pyfusion.pydecompose.pyeval_recall.py Evidence that never reaches the model at all.
3 A small financial dictionary The glossary is a short file of plain English definitions that gets pasted into the prompt whenever a relevant term shows up. Fair value hierarchy levels are the first entry, because the local model already misread them once during testing. glossary.jsonglossary_lookup.py Accounting concepts the model does not know well enough.
4 Checking the explanation This stage goes through the model's written reasoning line by line and asks whether each number quoted really appears where it says, and whether each calculation actually holds up. The people who built the benchmark asked for something like this in their own paper, and nobody has published it yet. verify_steps.pyfaithfulness_report.py Right answers reached through reasoning that does not hold up.
5 Where to draw the line The last experiment varies how often work gets passed from the local model up to the cloud one, from never to always. Never gives the cheapest possible system, always matches the published approach, and the interesting answer is somewhere in between. routing.pysweep_routing.py Cost, without giving up accuracy.
06

Questions for this meeting

Ordered by importance.

  1. Where should the line between the two models sit?

    My plan assumed the laptop model would only handle simple mechanical work. In testing it did the whole job correctly on its own. We could keep the cautious split, or hand the laptop model more and only involve the cloud when something looks wrong, or treat the split as something we measure rather than decide.

  2. Could you send the API keys, and which region is the Qwen account?

    DeepSeek should work from Canada with no setup at all. Qwen runs on Alibaba's cloud, which is divided into separate regions whose keys do not work across each other, so it would help to know which region your account sits in before I start testing.

  3. Is eight hours per experiment acceptable?

    That is the measured cost of running a hundred examples on my laptop. It works, but it means roughly one experiment per night. It is worth deciding now whether the larger runs should move to a free Colab GPU or a lab machine, rather than treating that as an emergency later.

  4. What are we aiming to produce at the end?

    A workshop paper, a technical report and a blog post each need different amounts of evidence behind them. The answer decides whether the official leaderboard submission and the full six hundred example runs are worth the time they cost.

  5. How interesting is the explanation checking to you?

    It is the most original part of the plan, and the people who built the benchmark asked for something like it in their own paper. It is also the obvious thing to focus on if current models turn out to already answer well. I would rather know your view before spending weeks on it.

07

What could go wrong, and the solution

If
Modern cloud models already score above 90%

Pivot from accuracy to faithfulness and cost. Both plans reuse the same infrastructure, and week 1 already produced a documented right-label / wrong-reasoning case to build on.

If
Table parsing overruns its estimate

Unparseable tables fall back to raw text whcih is what every published approach does for every table anyways. The floor is the status quo; every parsed table is upside.

If
Local throughput blocks the ablation cadence

Reduce retrieved chunk count first, since that helps precision too. Then shrink the slice, then move batches to Colab or a lab machine.

If
The 3B model proves too weak for a subtask

That subtask gets assigned to cloud, which is a data point for the routing analysis rather than a failure. The architecture treats this outcome as a finding.
